## 2. 🔴 Блокеры запуска

### Б1. Ни одна картинка на сайте не открывается (100 % изображений → HTTP 400)

Проверено: все 10 уникальных изображений отдают **400** через `next/image` и **200** напрямую из `/public`.

```
hero.jpg:        через next/image = 400,  файл напрямую = 200
cat-clinker.jpg: через next/image = 400,  файл напрямую = 200
… (все 10 файлов одинаково)
```

В логе pm2 — сотни строк `⨯ The requested resource isn't a valid image for /images/hero.jpg received null`.

**Причина (локализована).** При `basePath: "/stupeni"` Next 16 генерирует
`/stupeni/_next/image?url=%2Fimages%2Fhero.jpg`, а оптимизатор запрашивает `href` **без** basePath,
получает 404-HTML вместо картинки и отдаёт 400. Проверка:

* `?url=%2Fimages%2Fhero.jpg` → **400**
* `?url=%2Fstupeni%2Fimages%2Fhero.jpg` → **200 image/jpeg**

**Варианты фикса:**
1. **Основной** — деплой на собственном домене без `basePath` (это и так план запуска) → баг исчезает сам.
2. Пока живём на подпути: `src={withBase("/images/…")}` для `next/image` (проверено — такой url отдаёт 200)
   либо кастомный `images.loaderFile`, либо `images: { unoptimized: true }` как временная мера.

> Проверять после фикса **обязательно на живом деплое**, а не только локально: локально без basePath баг не воспроизводится.

### Б2. Заявки не доходят до Битрикс24 — они исчезают

`BITRIX_WEBHOOK_URL` не задан ни в `.env`, ни в окружении процесса (там только `PORT=3002`).
В `lib/bitrix.ts:64-68` при отсутствии вебхука `createLead` **пишет лид в лог и возвращает `ok: true`** —
пользователь видит «Заявка отправлена», в CRM ничего нет. В логе за всё время 2 строки
`[bitrix] lead (no webhook configured)`.

Что сделать: завести вебхук в окружении (не в коде), проверить сквозной проход в воронку
«Лендинг ступени/террасы», и **поменять поведение fallback**: без вебхука отдавать ошибку/писать в персист,
а не «успех». Заодно — тег заявки в отдельное поле сделки, а не только в `TITLE` (ТЗ E8), и решить
лид vs сделка (сейчас `toDealFields` шлётся в `crm.lead.add`).

### Б3. Яндекс.Метрики на сайте нет вообще

В HTML нет счётчика, `NEXT_PUBLIC_YM_ID` не задан, в `CookieBanner.tsx:10` честный комментарий
«…который читает загрузчик Метрики (**когда будет подключена**)». Инфраструктура согласия готова
(`window.__consent` + событие `consentchange`), самого счётчика нет.

Следствие: нулевая аналитика, ни одной цели, **рекламу Директа запускать не на что** — оптимизировать
и считать CPL будет нечем. Плюс не выполняются критерии приёмки §15/§19 и сквозная аналитика B.9.

### Б4. Один SKU — четыре разные цены, акция истекла 11 дней назад и всё ещё висит

`paradyz-taurus-brown`, ступень фронтальная (проверено на живом сайте):

| Где | Что показано |
|---|---|
| БД (`seed.ts`, `price_rub`) — **её же берёт калькулятор** | **1 890 ₽** |
| Витрина / сетка каталога (`ProductCard.tsx:36`) | 2 190 ₽ → **1 883 ₽** |
| Карточка товара (`ProductDetail.tsx:81-82`) | 1 890 ₽ → **1 625 ₽** |
| JSON-LD `Offer.price` (`jsonld.ts:57`) | **1 883 ₽** |

Причина: три разных трактовки промо. В карточке за «старую цену» берётся **текущая** цена и от неё
ещё отнимается 14 %. Клиент считает комплект по 1 890, а в карточке ему обещают 1 625.

Плюс: `ProductCard`/`ProductDetail` читают `product.promo` напрямую, а не `activePromo()` — акция
Taurus истекла `2026-07-15`, но бейдж «−14 %» и скидка показываются до сих пор. Это прямое нарушение
критерия приёмки «по истечении даты акция гаснет автоматически».

Ещё: `priceValidUntil` в JSON-LD подставляется из `price_updated_at` (**прошедшая** дата 2026-07-15) —
для Яндекса/Google это просроченный оффер.

**Фикс:** одна функция цены (`activePromo` + единая формула old/new) для витрины, карточки, JSON-LD
и калькулятора; `priceValidUntil` = дата в будущем (напр. +7 дней).

### Б5. Ссылка согласия 152-ФЗ ведёт на сайт агентства

`LeadForm.tsx:321` — сырой `<a href="/privacy">` без `withBase`. На подпути это уходит на
`br2nd.tech/privacy`, а там (проверено) отдаётся 200 и заголовок
«Hire a senior fullstack engineer · MVP foundation in 72 hours · br2nd».
То есть чекбокс «согласен с Политикой» ведёт на страницу другого бизнеса — согласие юридически дефектно.

Второй такой же случай: `app/offer/page.tsx:45` → `/payment-delivery`.
Остальные ссылки — `<Link>`, basePath обрабатывается корректно.

### Б6. Весь сайт под `noindex` (это правильно сейчас, но это переключатель запуска)

`NEXT_PUBLIC_PREVIEW=1` → `layout.tsx:38` ставит `robots: {index:false, follow:false}` на все страницы
(проверено: `noindex` в HTML на всех 17 проверенных URL). Для превью на домене агентства — верно.
При запуске: снять флаг, иначе сайта в поиске не будет.

## 3. Калькулятор — движок, баги, методика

### Что верно (проверено)

* Формулы `mode-a.ts` / `mode-b.ts` **дословно совпадают** с §9.1.3 / §9.2.6, включая
  `Lнакл = N×√(d²+h²)`, вычеты круглой/прямоугольной формы, запас по раскладке 5/8/10/12 %,
  выбор колонки HILST по площади, округление до целых упаковок материалов, цены по городу.
* Тесты сверяют результаты с примерами ТЗ §9.1.4 / §9.2.7 / §9.2.8 — 17/17, 39 assert.
* Опечатка `1200x200` → `1200x1200` исправлена (E2), немонотонная ячейка `600x1200` → 6.13 (E3).
* INP-паттерн B.5 реализован: `useDeferredValue` на марши/площадку/цены/участки.
* Элементы, которых нет у артикула, в UI скрыты (`stepAvailability`) — как требует §9.1.2.

### 🟠 К1. Размер базовой плитки не связан с артикулом → завышение ровно вдвое

`baseTileSize` («30×30 / 30×60») — независимый переключатель UI, а количество считается по
`TILE_PER_SQM`, игнорируя `per_sqm` базового элемента артикула (ТЗ §8.3: «если у артикула задан точный
`per_sqm` — берётся он»). При смене артикула переключатель не сбрасывается.

Реальный случай в текущем каталоге — **Exagres Base Grey** (база 300×600, 5.56 шт/м², 480 ₽/шт):

```
площадка 1,5 × 1,2 м
UI по умолчанию 30×30      → 21 шт × 480 ₽ = 10 080 ₽
фактический формат 30×60   → 11 шт × 480 ₽ =  5 280 ₽
завышение: 4 800 ₽ (ровно ×2)
```

Фикс: брать `per_sqm`/размер из элемента `base` артикула; переключатель показывать только когда у
артикула действительно есть оба формата.

### 🟠 К2. Состав расчёта не уезжает в CRM

ТЗ §12.3 требует в сделке: режим, город, бренд/артикул, формат, состав (штуки по элементам), способ
укладки, материалы/опоры, итого ₽, вес. Фактически в Б24 уходит одна строка вида
`Ступени, 2 марш(а/ей), Paradyz Taurus, 30x30` (`ModeAForm.tsx:330`) — ни количеств, ни суммы, ни веса.
Менеджер не видит, что именно посчитал клиент.

### 🟡 К3. Прочее по калькулятору

* **Нет цены за м²** — в UI только «цена за плиту, ₽» (`price_rub_pcs`), хотя движок умеет `pricePerSqm`,
  а в 1С керамогранит прайсуется в м². Для менеджеров это неудобно и провоцирует ошибки.
* **Нестандартный формат на опорах** → `pedestalsPerSqm` вернёт `null`, опоры молча не посчитаются
  (в текущем сиде все форматы есть в таблице, но при добавлении нового — тихий ноль). Нужен явный
  «индивидуальный расчёт».
* **Боковины марша** — только «оба борта» (`2 × Lнакл`); марш вдоль стены посчитается с лишним плинтусом.
* **Гравийная укладка** — не считает подсыпку/геотекстиль (по ТЗ так и есть, но продавать «на гравий»
  без основания странно).
* **Нет обязательных по ТЗ B.7/B.8 элементов**: shareable-расчёт по URL (в критериях приёмки),
  наличие/срок поставки в результате, оценка доставки по весу, PDF.
* В подписи результата нет даты актуальности цены и курса (B.9); дисклеймер «не является публичной
  офертой» есть только в карточке товара, в панели результата — формулировка «цены справочные».

### ⚠️ Данные калькулятора, требующие подтверждения (не баги — риск неверных смет)

1. **Таблица HILST не сверена поячеечно** с листом 37 ATP HILST LIFT (требование B.11 и критерий приёмки).
   Под вопросом три места: `800x800` третья колонка `6.71` (то же значение, что было ошибкой в `600x1200`),
   и полностью совпадающие строки `500x500` и `1000x1000`. Остальные значения на вид согласуются
   с логикой производителя (доп. опора под центром плиты >500 мм и дополнительные опоры под крупным
   форматом), поэтому речь именно о сверке, а не о переписывании таблицы.
2. **Расход сопутствующих материалов** взят из ТЗ и требует сверки с TDS: клей 5 кг/м² и особенно
   затирка 0,45 кг/м² выглядят низкими для клинкера с широким швом на улице. Ошибка здесь = недозаказ
   у клиента и рекламация.
3. **Цены опор HILST** (HL0–HL10) — с сайта hilst.ru на дату ТЗ, нужна актуализация.
4. **Методика фронтальных элементов.** Считается по общему погонажу марша, а не по ступеням.
   На примере ТЗ (N=5, W=1.5, 2 угла): по погонажу **4 шт**, «по ступеням без резки между ступенями» — **5 шт**
   (+25 %). Если бригада не переносит отрез ступени с капиносом с одной ступени на другую, комплект
   будет недозаказан. Нужно решение технолога: оставить погонаж (и, возможно, поднять запас) или считать
   по ступеням.

## 6. Фронтенд и вёрстка

**Сильно:** дизайн-система выдержана (направление B), контрастная палитра, `prefers-reduced-motion`,
`:focus-visible`, skip-link, `scroll-padding` под sticky-шапку (WCAG 2.2 §2.4.11), `:user-invalid/:user-valid`,
`aria-invalid`/`aria-errormessage`, `content-visibility` на карточках, View Transitions, scroll-driven параллакс,
доступный `Modal` (focus-trap, Esc, возврат фокуса, блокировка скролла), мобильное меню.

Проблемы:

1. **Без JS сайт визуально пустой.** `Reveal` рендерится с классом `reveal` (`opacity: 0`), видимость
   включает IntersectionObserver. Любая ошибка JS/блокировка = белые секции (в HTML контент есть, поэтому
   для краулеров ок, для людей — нет). Нужен `<noscript>`-фолбэк или инверсия логики.
2. **Вес первой загрузки 230 КБ gzip** (14 JS + 1 CSS) против бюджета ТЗ «JS < 130 КБ gzip». HTML главной
   263 КБ несжатого — в RSC-payload сериализуется весь сид-каталог (виден целиком в исходнике страницы).
3. **Мобильная сетка калькулятора, режим B:** строки участков — `grid-cols-[auto_1fr_1fr_1fr_auto]`
   без брейкпоинтов, вычеты — `[1fr_1fr_1fr_auto]`. На 320–360 px это 3 поля + кнопка в одну строку;
   проверить и переложить в стопку.
4. Соцсети в футере — **`<span>`, а не ссылки** (VK/TG/WA не кликаются); в шапке иконок мессенджеров нет,
   хотя §6 блок 1 их требует.
